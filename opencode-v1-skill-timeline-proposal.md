# Project Proposal: OpenCode v1 `/skill-timeline` Plugin

## Status

- **Target:** OpenCode **v1**
- **Release status:** Beta (`0.1.0-beta.2`)
- **Pinned host:** OpenCode `1.18.27`
- **Form:** TUI plugin
- **Command:** `/skill-timeline`
- **Primary goal:** Make skill usage in a session easy to audit without manually reading the full conversation/tool output.

This project is intentionally scoped to **OpenCode v1**. OpenCode v2 uses a new, incompatible plugin API and should be treated as a separate future port rather than part of the first implementation.

---

## 1. Problem

OpenCode sessions can contain many tool calls and long agent outputs. Skills may be invoked somewhere in that stream, but there is no convenient session-level view answering:

- Which skills were called?
- What was happening immediately before each skill call?
- When was each skill called?
- Where in the session did the call happen?

Today, verifying something simple such as:

> Did the agent run `plugin-review` before preparing this release?

can require searching or manually reading a long transcript.

The existing built-in `/timeline` UI already provides a good interaction model for reviewing session history. `/skill-timeline` should provide the same kind of compact, searchable review experience specifically for skill calls.

---

## 2. Proposed UX

Running:

```text
/skill-timeline
```

opens a modal visually and behaviorally similar to OpenCode's built-in `/timeline`.

### Layout

Three columns:

```text
Context right before skill call            Skill called          Timestamp
────────────────────────────────────────────────────────────────────────────
review plugin before preparing release     plugin-review         5:01 PM
investigate why conversation layout broke  frontend-debugging    4:04 PM
check tests before merging                  testing               3:46 PM
inspect release requirements                release               3:31 PM
```

The first column should take most of the width.

### Interaction

The modal should support:

- `↑` / `↓` to move between entries
- typing to search/filter
- `Esc` to close
- `Enter` to locate the selected call in the session, where the v1 TUI API permits reliable navigation

Search should match both:

- skill name
- context text

Example:

```text
Search: review
```

could match both `plugin-review` and any context containing the word "review".

---

## 3. User Story

As an OpenCode user, I want to open `/skill-timeline` and immediately see every skill invocation in the current session, together with the context that led to it, so I can audit agent behavior without reading the entire transcript.

Typical questions it should answer:

- Did the agent call the required review skill?
- Did it call the skill before or after making changes?
- Was the same skill called repeatedly?
- What task was the agent working on when it called the skill?
- When exactly did the call occur?
- Can I jump back to the relevant point in the session?

---

## 4. Scope

### In scope for v1

- OpenCode v1 TUI plugin
- `/skill-timeline` slash command
- Native modal/picker UI
- Current-session skill-call extraction
- Three-column display:
  - context immediately before the call
  - skill name
  - timestamp
- Search/filter
- Keyboard navigation
- Repeated skill calls shown individually
- Failed skill calls still shown
- Best-effort jump/location behavior
- No model invocation required to build the timeline

### Out of scope for the first version

- OpenCode v2 support
- Aggregate skill statistics
- Cross-session analytics
- Skill success scoring
- Automatic summaries generated by an LLM
- Tool calls other than skills
- Subagent-tree visualization
- Editing or replaying session history

These can be future extensions.

---

## 5. OpenCode v1 Plugin Requirement

This project should be implemented against the **OpenCode v1 plugin/TUI API**, not the v2 API.

Recent v1 builds expose TUI facilities such as:

- `api.keymap.registerLayer(...)`
- slash-command metadata via registered keymap commands
- `api.ui.dialog`
- `api.ui.Dialog*`
- `api.route.register(...)`
- `api.route.navigate(...)`
- `api.client`
- `api.event`

The older `api.command.*` interface is deprecated in current v1 source in favor of `api.keymap.registerLayer(...)`.

Therefore the implementation should target the current v1 TUI API rather than older examples that use only:

```ts
api.command.register(...)
```

A compatibility shim for older v1 releases can be considered later if needed, but it should not complicate the first implementation.

---

## 6. OpenCode v2 Compatibility

OpenCode v2 is **not plugin-compatible with v1**.

The official OpenCode migration guide states that:

- v2 uses a new plugin API
- v1 plugins will not work in v2
- plugin implementation code must be ported
- the v2 plugin API is still beta and may continue changing

Therefore:

```text
v1 implementation
      │
      └── not expected to load in v2
```

A future v2 port should be maintained as a separate compatibility target.

Possible structure:

```text
skill-timeline/
├── packages/
│   ├── v1/
│   │   └── OpenCode v1 plugin
│   └── v2/
│       └── future port
└── packages/core/
    └── shared timeline extraction logic, if practical
```

For an initial small project, a simpler single-package v1 repository is preferable.

---

## 7. Does OpenCode v2 Improve Skill-Call Reviewing?

### Short answer

**It improves the underlying data model, but not enough to replace this plugin's UI.**

OpenCode v2 makes skills more explicit in the runtime. It has a first-class native `skill` tool and structured tool-call/session identifiers, which should make a future v2 implementation cleaner.

However, this does not automatically solve the review problem:

```text
structured skill call data
          ≠
easy skill-call review UI
```

The user still benefits from a dedicated timeline showing only skill invocations.

So the project remains useful even if a v2 port is created later.

### Implication for this project

Do **not** delay the v1 plugin waiting for v2.

Instead:

1. Build the useful v1 plugin now.
2. Keep the extraction layer conceptually separate from the TUI.
3. Re-evaluate the v2 API once it stabilizes.
4. Port the UI/data adapter separately.

## 8. Data Model

Each displayed row should be represented internally by something similar to:

```ts
interface SkillTimelineEntry {
  sessionID: string
  messageID?: string
  anchorMessageID?: string
  callID?: string

  skill: string
  timestamp: number

  context: string

  status?: "running" | "completed" | "error"
}
```

Only these fields are required for the initial UI:

```text
context
skill
timestamp
```

Identifiers should still be retained internally because they may enable jump-to-location behavior.

---

## 9. Detecting Skill Calls

The extractor should operate on structured OpenCode session/tool data whenever possible.

Conceptually:

```text
current session
     ↓
session messages / parts / tool events
     ↓
identify skill invocations
     ↓
extract skill name + timestamp + call identifier
     ↓
resolve preceding visible context
     ↓
SkillTimelineEntry[]
```

Do not parse rendered terminal text if structured session data is available.

Do not rely only on a new append-only log created after plugin installation, because that would prevent reviewing older calls already present in the current session.

A runtime hook may still be useful for keeping the modal updated while a session is running, but persisted/structured session data should remain the source of truth where practical.

---

## 10. Defining "Context Right Before Skill Call"

This needs a deterministic rule.

The plugin should not ask an LLM to summarize the context.

### Priority 1: nearest preceding visible assistant text

Example:

```text
assistant:
The release changes are complete. I should run the plugin review before merging.

skill:
plugin-review
```

Timeline:

```text
The release changes are complete. I should…   plugin-review   5:01 PM
```

### Priority 2: nearest preceding user message

If the assistant calls the skill immediately without visible text:

```text
user:
Review the plugin before publishing.

assistant:
skill(plugin-review)
```

Timeline:

```text
Review the plugin before publishing.          plugin-review   5:01 PM
```

### Priority 3: fallback

If no useful visible context can be found:

```text
—                                             plugin-review   5:01 PM
```

### Context formatting

For display:

- collapse line breaks
- collapse repeated whitespace
- strip or simplify Markdown where useful
- truncate according to terminal width
- preserve full context internally for search

Suggested maximum untruncated context length:

```text
200–300 characters internally
```

The rendered row can use much less.

---

## 11. Timestamp Selection

Prefer the timestamp associated with actual skill-tool execution.

If the tool data exposes start time:

```text
start timestamp → preferred
```

If only message creation time is available:

```text
message timestamp → fallback
```

Display should follow the user's current OpenCode time formatting conventions, ideally matching `/timeline`.

Example:

```text
5:01 PM
```

rather than inventing a separate format.

---

## 12. Modal Design

The visual goal is to look like a sibling of built-in `/timeline`, not a custom dashboard.

Suggested structure:

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│ Skill Timeline                                                        esc   │
│                                                                              │
│ Search                                                                       │
│                                                                              │
│ Context                                      Skill                  Time      │
│ review plugin before preparing release       plugin-review          5:01 PM   │
│ investigate conversation panel regression    frontend-debugging      4:04 PM   │
│ verify tests before merge                     testing                 3:46 PM   │
└──────────────────────────────────────────────────────────────────────────────┘
```

### Responsive behavior

Priority when terminal width shrinks:

1. keep skill name visible
2. keep timestamp visible
3. shrink/truncate context

The skill column should have a sensible maximum width.

Example:

```text
Context: flexible
Skill:   20–28 characters
Time:    8–10 characters
```

## 13. Command Registration

Preferred command:

```text
/skill-timeline
```

Suggested command metadata:

```text
name: skill-timeline
title: Skill Timeline
category: Session
description: Review skill calls in the current session
```

For current v1 TUI APIs, prefer registering through:

```ts
api.keymap.registerLayer({
  commands: [
    {
      name: "skill-timeline.open",
      title: "Skill Timeline",
      category: "Session",
      namespace: "palette",
      slashName: "skill-timeline",
      run() {
        // open modal
      },
    },
  ],
})
```

Exact types should be verified against the OpenCode v1 version selected for development.

## 14. Locating a Skill Call

The most useful behavior after selecting a row is:

```text
Enter
  ↓
close /skill-timeline
  ↓
navigate or scroll to the corresponding call
```

The plugin should retain:

- message ID
- part/tool-call ID
- session ID

where available.

### Preferred behavior

`Enter` locates the tool call or its containing message without altering history.

The v1 implementation anchors each call to the user message that began its turn and uses the renderer tree to mirror the built-in `/timeline` scroll behavior.

### Important constraint

This command is an **inspection tool**, not a rewind command.

It must not:

- fork the session
- delete later messages
- revert conversation state
- replay the skill

If the v1 TUI API does not expose a reliable public scroll-to-message primitive, the first release may use a fallback:

- close modal
- navigate to the containing session/message if possible
- show/copy the call/message identifier
- or temporarily omit `Enter` navigation while keeping the timeline itself functional

The data model should still preserve identifiers so proper navigation can be added later.

---

## 15. Search

Search should be local and instant.

It should match:

```text
entry.skill
entry.context
```

Case-insensitively.

Examples:

```text
review
plugin-review
release
tests
```

No model/API call should occur while searching.

---

## 16. Ordering

Default order should match the built-in timeline convention.

For reviewing recent activity, newest-first is likely the most natural:

```text
5:01 PM
4:36 PM
4:23 PM
...
```

If the built-in `/timeline` orders entries newest-first, `/skill-timeline` should follow it exactly.

Stable ordering must be maintained when multiple calls share the same timestamp by falling back to original session order.

---

## 17. Repeated Calls

Every invocation should appear separately.

Example:

```text
fix remaining unit failures                  testing       5:10 PM
run tests after first patch                  testing       4:58 PM
verify original failure                      testing       4:43 PM
```

Do not deduplicate by skill name.

This is an audit timeline, not a list of available skills.

---

## 18. Error and Running States

A failed skill invocation still matters.

The timeline should therefore include:

- completed calls
- failed calls
- currently running calls

The first version does not need a visible status column.

Possible lightweight indication later:

```text
testing        5:01 PM
plugin-review  4:53 PM  !
release        4:41 PM
```

But status should not expand the initial three-column design unless necessary.

---

## 19. Architecture

Separate extraction from rendering.

```text
OpenCode session data
        │
        ▼
SkillTimelineExtractor
        │
        ▼
SkillTimelineEntry[]
        │
        ▼
SkillTimelineModal
```

### `SkillTimelineExtractor`

Responsibilities:

- obtain current session data
- identify skill tool calls
- extract skill names
- extract timestamps
- determine preceding context
- retain navigation identifiers
- return normalized entries

No TUI rendering logic.

### `SkillTimelineModal`

Responsibilities:

- render three columns
- search/filter
- keyboard selection
- responsive truncation
- close behavior
- invoke locate/jump action

### Command layer

Responsibilities:

- register `/skill-timeline`
- get current session
- open modal

### Extraction tests

Test sessions containing:

- zero skill calls
- one skill call
- repeated calls
- multiple different skills
- failed calls
- calls without preceding assistant text
- calls immediately after user input
- multiple calls in one assistant turn
- long context
- multiline context
- equal timestamps

### UI tests/manual checks

Verify:

- `/skill-timeline` opens
- `/skill-timeline` is discoverable in slash-command completion
- layout resembles `/timeline`
- search filters instantly
- arrow navigation works
- `Esc` closes
- terminal resize behaves correctly
- long skill names do not destroy layout
- empty state is clear

Suggested empty state:

```text

```

## 22. Performance

The command should have near-zero overhead while unused.

Opening it may scan the current session once:

```text
O(number of message/tool parts)
```

That is acceptable for normal sessions.

Possible optimization for very large sessions:

- maintain an in-memory cache
- append new skill entries from events
- invalidate cache when session history changes

Do not add caching until needed.

---

## 23. Privacy and Model Usage

`/skill-timeline` should be entirely local to OpenCode session data.

It should:

- make no LLM call
- send no analytics externally
- not expose hidden reasoning
- use only visible conversation text for the context column

This makes it suitable as an audit/debugging feature.

## 25. Acceptance Criteria

The v1 project is complete when:

1. It installs and loads as an **OpenCode v1 TUI plugin**.
2. `/skill-timeline` appears as a slash command.
3. Running it opens a modal styled similarly to `/timeline`.
4. Every skill invocation in the current session appears exactly once.
5. Each row shows:
   - context right before the call
   - skill called
   - timestamp
6. Repeated calls are shown independently.
7. Search matches skill names and context.
8. Arrow-key navigation works.
9. `Esc` closes the modal.
10. No LLM call is required.
11. Context is derived only from visible session text.
12. Existing session data is used where possible rather than only logging calls made after plugin startup.
13. Selection retains enough identifiers for reliable locate/jump behavior.
14. The plugin does not claim v2 compatibility.

## 26. Recommended Development Order

### Phase 1 — Verify v1 API surface

Before implementation, pin a specific OpenCode v1 release and verify:

- current TUI plugin loading
- `api.keymap.registerLayer`
- slash-command registration
- dialog APIs
- session/client APIs
- tool-call representation
- any scroll/navigate-to-message primitive

This matters because the v1 TUI plugin API itself changed during the v1 lifecycle.

### Phase 2 — Extractor

Implement:

```text
session → SkillTimelineEntry[]
```

with unit tests.

### Phase 3 — Modal

Clone the interaction patterns of built-in `/timeline` as closely as the public TUI API permits.

### Phase 4 — Command

Register `/skill-timeline`.

### Phase 5 — Locate

Add `Enter` navigation if supported cleanly by the v1 API.

### Phase 6 — Hardening

Test:

- long sessions
- repeated skills
- errors
- terminal resizing
- plugin reloads
- current OpenCode v1 release

## 27. Main Technical Risks

### Risk 1: v1 TUI API churn

OpenCode v1 changed its command registration API during the v1 series. Older `api.command.*` examples may not match current v1 behavior.

**Mitigation:** pin and develop against a known current v1 version; use the current `api.keymap`/TUI interfaces.

### Risk 2: Jump-to-call API

The public TUI plugin API may not expose exactly the same internal navigation primitive used by built-in `/timeline`.

**Mitigation:** make jump-to-call a separable feature. The timeline is still valuable without it, and identifiers should be retained for a later implementation.

### Risk 3: Identifying "skill" consistently

Skill calls must be detected from structured session/tool data, whose exact shape should be verified against the pinned v1 build.

**Mitigation:** isolate version-specific extraction in `extract.ts`.

### Risk 4: OpenCode v2 incompatibility

A working v1 plugin will not automatically work on v2.

**Mitigation:** explicitly label the project as v1 and plan a separate port once the v2 API stabilizes.

## 28. Deliverable

A small OpenCode v1 plugin that turns skill usage from something buried in transcript output into a first-class review surface:

```text
/skill-timeline
        ↓
┌──────────────────────────────────────────────────────────────┐
│ Context before call              Skill              Time      │
│ ...                              ...                ...       │
└──────────────────────────────────────────────────────────────┘
```

The plugin should feel like a natural extension of OpenCode's existing `/timeline`, but specialized for auditing skill invocation.
